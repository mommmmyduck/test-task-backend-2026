# Синхронизация CRM

## Что было дорого

`collect_leads_customers()` искал каждую запись через JSONB-запрос, фиксировал
транзакцию после каждого покупателя или сделки, а затем повторно загружал всю
таблицу для очистки. Ошибки обработки сделок подавлялись, поэтому неполный
проход мог завершиться очисткой данных.

## Что изменено

- Существующие записи загружаются один раз. В памяти строятся индексы по CRM ID
  и логинам; повторных поисковых SELECT на каждую сущность нет.
- JSONB обновляется присваиванием нового списка, а изменения, слияния и полная
  очистка фиксируются одной транзакцией.
- Полная очистка выполняется только после успешного исчерпания обоих CRM
  итераторов. Любая ошибка приводит к rollback и передаётся вызывающему коду.
- Поиск по CRM ID имеет приоритет. По логину используется только единственная
  запись; при совпадении разных записей сделки они сливаются в запись сделки.
- Полный снимок удаляет отсутствующие сущности и записи, а также сущности с
  «удалить» в имени. Покупатель без логина пропускается.

## Запросы и память

Для 20 тыс. покупателей и 50 тыс. сделок выполняется один SELECT существующей
таблицы вместо поиска по каждой из 70 тыс. сущностей и повторного чтения для
очистки. Записи создаются, обновляются и удаляются при одном flush/commit;
SQLAlchemy группирует однотипные изменения в executemany. Поэтому число
исполнений зависит от сочетания изменившихся JSONB-полей и драйвера, но не
растёт на один SELECT/commit для каждой сущности. Плюс остаются запросы клиента
к CRM; адаптер получает следующую страницу по `_links.next.href`.

CRM итераторы не буферизуются. Память пропорциональна уже сохранённому JSONB,
индексам и наборам ID текущего снимка. Грубая оценка для 70 тыс. сущностей при
среднем сериализованном payload 1–3 КБ: порядка 200 МБ–1 ГБ пикового RSS,
включая Python-представление JSON, SQLAlchemy-объекты и индексы. Это диапазон,
а не гарантия: фактический размер определяется вложенными `api_value`,
контактами и компаниями. Для точной оценки следует замерить RSS на выборке
реальных данных и масштабировать по суммарному размеру загруженного JSONB.

## Что оставлено

Формат существующих JSONB-полей сохранён, поэтому поиск по точному логину и
названию в других частях приложения остаётся возможным, как и связь сделки с
покупателем через общую запись. Схема БД не меняется. Локальный прогон с CRM и
PostgreSQL не выполняется: для этого задания нет авторизованной конфигурации
CRM или тестовой базы.

## Ограничения

Одна транзакция охватывает загрузку существующих записей, получение и обработку
CRM-данных и, для полного прохода, очистку снимка. Это упрощает атомарность
синхронизации: при ошибке изменения откатываются и очистка не выполняется. При
медленном API транзакция может оставаться открытой дольше, увеличивая время
удержания транзакции и возможных блокировок.
